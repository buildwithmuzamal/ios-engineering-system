# Phase 11 — Open Source & Code Reading

> **Purpose:** Learn how to understand, evaluate, contribute to, and maintain real-world codebases. Great engineers spend as much time reading code as writing it.

---

# Goal

Become comfortable navigating unfamiliar projects, learning from experienced engineers, and contributing meaningful improvements to open source.

---

# Learning Outcomes

By the end of this phase you should be able to:

- Read large codebases without feeling overwhelmed.
- Trace data flow through unfamiliar projects.
- Review pull requests effectively.
- Contribute to open-source projects.
- Learn engineering practices from production code.

---

# Module 1 — Reading Large Codebases

## Core Topics

- Project structure
- Entry points
- Feature navigation
- Data flow
- Dependency graph

---

## Learning Objectives

After completing this module you should be able to:

- Understand Project structure and recognize when it is the right tool.
- Understand Entry points and recognize when it is the right tool.
- Understand Feature navigation and recognize when it is the right tool.
- Understand Data flow and recognize when it is the right tool.
- Understand Dependency graph and recognize when it is the right tool.
- Apply the module concepts in the mini project without copying a full solution.
- Use official documentation as the primary reference for this module.

---

## Parallel Learning Layers

### Git

- Follow contribution Git etiquette.
- Rebase or merge according to project guidelines.
- Write commits that are easy for maintainers to review.

### Xcode

- Canvas
- Preview
- Live Preview
- View Debugger

### Apple Documentation

- SwiftUI documentation for: Project structure, Entry points, Feature navigation, Data flow

### WWDC

- SwiftUI sessions matching this module

### Best Practices

- Prefer clarity when working with Project structure.
- Keep responsibilities small and names meaningful.
- Validate understanding with a working example before moving on.

### Design Thinking

- What problem does Project structure solve?
- What would a simpler alternative look like?
- What trade-offs appear if this is overused?

### Architecture Thinking

- Where does this concept belong in a production app?
- What should stay out of the UI layer?
- How would this decision affect testing and change later?

### Open Source

- Study view structure in a small SwiftUI open-source app

### AI

- Ask AI to explain Project structure after you attempt it yourself.
- Request a review of your design, not a full generated solution.
- Challenge AI suggestions against Apple documentation.

### English

- Write a short explanation of Project structure in your own words.
- Use precise terminology in notes and commit messages.
- Practice explaining trade-offs as you would in a pull request.

### Notes

- Document Project structure, Entry points, Feature navigation, Data flow.
- Capture common mistakes and Apple recommendations.
- Link related modules and future spiral topics.

### Reflection

- Can I teach Project structure to another engineer?
- What is still unclear?
- How does this connect to previous phases?

---

## Mini Project

- Build a small focused exercise that proves you understand Project structure.
- Keep the scope small enough to finish, but realistic enough to reuse later.
- Document one design decision and one mistake you corrected.

---

## Exit Criteria

You should be able to:

- Use Project structure correctly in a realistic scenario and explain the trade-offs.
- Use Entry points correctly in a realistic scenario and explain the trade-offs.
- Use Feature navigation correctly in a realistic scenario and explain the trade-offs.
- Use Data flow correctly in a realistic scenario and explain the trade-offs.
- Finish the mini project and describe one design decision you made.
- Write permanent notes covering the core topics, mistakes, and Apple guidance.
- Meet every Learning Objective for this module.
